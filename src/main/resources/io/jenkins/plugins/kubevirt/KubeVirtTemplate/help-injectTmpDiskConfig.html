When enabled (default), a 10Gi ephemeral disk will be attached to the VM and mounted at /tmp via cloud-init. This provides faster temporary storage for build operations.

What this does:

  • Attaches an emptyDisk volume (10Gi) as a third disk to the VM
  • Injects cloud-init runcmd commands to format and mount it at /tmp
  • The disk is ephemeral - data is lost when the VM is deleted

When to enable:

  • Builds that create many temporary files
  • VMs where the root disk has limited space or slower storage
  • Workloads that benefit from dedicated /tmp performance

When to disable:

  • In case you changed the default Free Space Threshold in Node Monitors, as agents might be marked offline
  • Simple builds with minimal temp file usage
  • VMs that already have adequate /tmp space on the root disk
  • When you want full control of cloud-init configuration

Cloud-Init Code Injected:

The following runcmd script will be automatically added to your cloud-init configuration:

runcmd:
  - |
    TMP_DISK=/dev/vdc
    if [ -b "$TMP_DISK" ]; then
      # Create filesystem if not already present
      if ! blkid "$TMP_DISK" | grep -q ext4; then
        mkfs.ext4 -F "$TMP_DISK"
      fi
      # Create mount point and mount
      mkdir -p /mnt/tmp
      mount "$TMP_DISK" /mnt/tmp
      # Move existing /tmp contents and remount
      rsync -a /tmp/ /mnt/tmp/ 2>/dev/null || true
      umount /mnt/tmp
      mount "$TMP_DISK" /tmp
      chmod 1777 /tmp
      echo 'Successfully mounted /tmp disk'
    else
      echo 'Warning: /tmp disk not found at $TMP_DISK'
    fi

Notes:

  • The disk appears as /dev/vdc (after rootdisk and cloudinit disks)
  • If you already have a runcmd: section in your cloud-init, this script will be prepended to it
  • The script safely handles existing /tmp contents by copying them to the new mount
  • The chmod 1777 ensures proper sticky bit permissions for /tmp
